# Open work

The goal is that Gemstone decides once and both clients read that decision. Shared rules, records, sessions and orchestration live in Core; rendering, observation, scheduling, OS ports and locale formatting live in the apps. A view model, UI model, aggregate, factory or provider that still decides, re-derives, composes text or formats a number is debt; a model that holds one Core record and maps it to platform values is the target shape. Contracts and worked examples are in [ARCHITECTURE.md](ARCHITECTURE.md).

Every open item carries a stable id and a size (**S**/**M**/**L**). Ids are never reused. The namespaces in use are `VM` (consolidation into Gemstone: view state, decisions, numbers and text, twins, crossings, orchestration, stores), `AUD` (correctness and repeated work found by review), `D` (a product or security choice), `X` (blocked upstream) and `BD` (behavior differences awaiting triage); older namespaces appear only in the ledger. **Delete an item's line in the commit that lands it**; an item that turns out to be correct as written is closed the same way, with the reason moved to the ledger at the bottom.

Each new item was confirmed by reading both apps and the Core owner before it was written, and a defect two lenses found is one item. This is a plan, not a claim that the proposed records or checks already exist. Do not add duplicate tasks to reach a count.

## Working one item

Pick one item by its stable id and use the screen map to find its current owner. Source paths and line numbers are retrieval hints, not proof that an old finding still applies. Read the owner, both consumers and the linked architecture example before editing; closed ledger entries are dated rationale, not current completion claims.

Keep the implementation plan in the task update: the existing owner to change, the app path to delete, any real prerequisite and the exact relevant checks. Do not create a new planning artifact, service, session, cache or framework unless the current contract requires it. If a pure projection or existing record answers the question, use it. Preserve examples in the docs and correct them in place when signatures change. Check related ids before changing a shared owner: reuse one contract change and its regression fixtures rather than implementing competing fixes. Items that name each other ("land with …") share a record; land them in one change or in dependency order.

Use [Task Workflow](../skills/task-workflow.md) for execution and [Quality Checks](../skills/quality-checks.md) for verification. Implement ready work autonomously; the items in [Decisions to make](#decisions-to-make) require a product or security choice, and [Blocked upstream](#blocked-upstream) records external prerequisites. Shared infrastructure work gates only the consumers that need it; unrelated ready items need not wait.

## 1. Correctness and swallowed failures

Transaction-critical input, a user-visible outcome that a swallowed error hides, a write that runs when nothing changed, and a policy the two apps run on different triggers. Work these before anything below.

- **AUD5** **M** **Bug — a sent transaction that fails to record leaves no local row and no tracking.** [`store_pending`](../core/gemstone/src/services/confirm/mod.rs) calls `record(...).unwrap_or_default()`, so a failed `add_transactions` write becomes an empty list: no pending row is stored, `track` is handed nothing, and `execute` returns `Sent` as if everything succeeded. The funds are on chain and the activity sync will eventually fetch the transaction, so what is lost is local visibility and state polling, not funds. Do not route the outcome through the confirmation result: both apps read only `hashes` from `GemExecuteResult::Sent` ([iOS](../ios/Features/Transfer/Sources/ViewModels/ConfirmTransferSceneViewModel.swift), [Android](../android/features/confirm/viewmodels/src/main/kotlin/com/gemwallet/android/features/confirm/viewmodels/ConfirmViewModel.kt)), and its `transactions` payload was removed as dead FFI weight, so a new field or enum there would be read by nobody. This needs the product answer first — a warning on the success screen, a silent retry of the write, or documented reliance on the next activity sync — then one implementation at the owner. Cover the `Broadcast` error path too, where `store_pending` already runs for a partial broadcast.
- **AUD59** **S** **Needs a decision — surface the first balance fetch after enabling an asset.** [`refresh_enabled_assets`](../core/gemstone/src/services/balance/mod.rs) runs `let _ = self.update(...)` from `set_assets_enabled` and `setup_wallet`, so a just-enabled token sits at zero with no error until a refresh. Returning the failure alone does not help: both apps only `debugLog` a failed toggle, and iOS `AssetSceneViewModel.onSelectEnable` would drop its "asset shown" toast although the asset was enabled; side-effect callers (fiat quote, reward redemption, transaction post-processing, discovery) would fail their own action on a balance fetch. Decide how the failure is shown (a per-asset load state on the row, or an error toast after a successful enable), then return it from the user-facing toggles only and give the side-effect callers a write-only enable. The validator-name half landed on 2026-09-23.

## 7. Orchestration, services and stores

Core has no runtime, so scheduling, timers and OS callbacks stay in the apps; what moves is the decision — what to do, in what order, under what condition — returned as one call or one record. And [a store returns what Core reads](ARCHITECTURE.md#4-the-store-trait-is-the-apps-only-persistence-obligation), through one trait per responsibility.

- **VM78** **S** **Settings holds one service.** iOS `SettingsViewModel` holds `GemNotificationsService` only to call `enableForSupport`; the owning service should expose it (Android routes it through `EnablePushForSupport`).
- **VM79** **S** **The root scene stops reading the wallet store.** iOS [`RootSceneViewModel`](../ios/Gem/ViewModels/RootSceneViewModel.swift) reads `stores.walletStore.getWallet` directly; the session service answers the current wallet. Blocked on a synchronous answer: `GemWalletSessionService::get_current_wallet` is async (the wallet store port is async), and the root view needs the wallet on its first render or it flashes onboarding at every launch; either the port gains a synchronous read or the root keeps a stored wallet it can seed before first render.
- **VM86** **M** **Core preference changes are observable.** Both apps mirror Core preferences in observable objects and reload them by hand after the last wallet is deleted (Android `UserConfig`, iOS `ObservablePreferences.reload(after:)`).
- **VM88** **M** **Info sheets come from Core.** Around 25 topics are written twice: iOS [`InfoSheetModelFactory`](../ios/Features/InfoSheet/Sources/Factory/InfoSheetModelFactory.swift) (252 lines) and Android `InfoBottomSheet` (414 lines) each choose title, description, image and docs link; Core has `GemInfoTopic` but no sheet content.
- **VM89** **S** **Docs links come with the screen.** Screens pick docs URLs themselves (`StakeSceneViewModel` `.staking(chain)`, `ConnectionsViewModel` `.walletConnect`). Waits on the per-screen config decision raised on 2026-09-24 (generated constants and config on flow records instead of one-off exports): a docs link per screen is that kind of fixed data.
- **VM162** **S** **The launch is one Core call that owns its preference steps.** Both apps sequence three Core calls themselves and run one of them twice: iOS `App.swift:58-63` (`configure()` then `appStartService.run()`), `OnstartService.swift:62-74` (`setupWallets()` after the V3 keystore migration), `RootSceneViewModel.swift:112-120,138-145,173-180` (`setupWallet(wallet)` from `onChangeWalletId`, fired with `initial: true`); Android `MainViewModel.kt:127-138` (`run()` in one coroutine, migrations then `setupWallets()` in another), `AppViewModel.kt:107-116` (`setupWallet(session.wallet)` on the first session). In [`app_start/mod.rs`](../core/gemstone/src/services/app_start/mod.rs) `run` calls `ensure_default_assets`, `setup_wallets` calls `balance.setup_wallet` for every wallet, and `setup_wallet` calls both again for the current wallet, so every launch does the current wallet's balance setup and the default-asset ensure twice on both apps, with the ordering left to each app's task layout. `setupCurrency(locale)` and `incrementLaunchesCount` likewise run from unrelated places (iOS `OnstartService`, Android `SessionCoordinator` and `UserConfig`). `GemAppStartService` gains `launch(locale)` that runs `run`, `setup_wallets`, `setup_wallet` for the current wallet and the two preference steps once, in Core's order; `setup_wallet` stays for a wallet switch. Delete the `run()`/`setupWallets()` pair and its sequencing on both apps; the keystore migrations stay as ports. Folds VM85 and calls AUD57's `ensure_current_wallet` first. Open design points: both apps also run `setup_wallet` from their first wallet-id emission (iOS `onChange(initial: true)`, Android the first session), so either they skip that emission or Core owns the dedupe; iOS gates wallet setup behind the app unlock while `run` does not, so one call either delays device sync and config behind the unlock or reads the keystore before it; and Android's `SessionCoordinator` reads the currency once, so moving `setup_currency` into an async call leaves it on USD after a first install unless the locale reaches `GemPreferencesService` at construction.
- **VM164** **S** **The stores return what Core reads.** `GemPendingTransaction { wallet: Wallet, transaction }` ([`transaction_state/model.rs`](../core/gemstone/src/services/transaction_state/model.rs)) while Core reads `pending.wallet.id` only and `get_transaction`'s caller never reads `wallet`; both adapters build the wallet join themselves (iOS `TransactionStateStore.swift:23-31` loads every wallet into a dictionary and makes three reads per transaction, Android `TransactionStateStore.kt:20-25` `walletStore.getAllNow().associateBy`). `GemBalanceStore::get_available_balances` is fetched for `asset_id` only in `setup_wallet` and `add_missing_balances`; `GemAssetStore::get_assets` is loaded on every balance write for `decimals` only; `get_wallets` for `wallet.index`. Narrow the record to `wallet_id` and add `get_balance_asset_ids` and `get_asset_decimals`. Delete the wallet joins in both adapters and the iOS `getAssetIds`/`getDelegationIds` that load full rows.

## Decisions to make

None of these is a code change until someone chooses; each is written so the choice is the only remaining step.

- **D74** **S** **How many banners a screen shows.** iOS `WalletScene.swift:50` and `AssetScene.swift:36` show only `visibleBanners.first`; Android `BannersScene.kt:44-67` pages through every visible banner in a `HorizontalPager`. Core orders `visible_banners` by state and event priority ([`banner/rules.rs`](../core/gemstone/src/services/banner/rules.rs)) and hands back the whole list, so how many a screen shows is decided twice. Choose one; then `GemBannerContext::visible_banners` returns one row or says how many, and the losing side (`.first` or the pager) goes.
- **D76** **S** **Whether one failed balance request discards its network's other answers.** `chain_balances` in [`balance/mod.rs`](../core/gemstone/src/services/balance/mod.rs) joins the coin, staking, token and earn results with `?`, so a failed staking or earn request throws away the coin and token balances that succeeded on that network, and no test covers the case; the product intent in [product/wallet.md](product/wallet.md) says a slow or failing request must not hold back the others. Options: publish the components that answered and return the first component failure (extend `published_balances` to per-component results, add the test); or keep the network all-or-nothing and write that down as the rule.
- **D77** **S** **When the wallet list updates during a balance refresh.** `update` waits for every network (`join_all`) and every component (`join!`) before its single write, so the fastest network's coin balance shows only when the slowest has answered or failed; [ARCHITECTURE](ARCHITECTURE.md#publish-a-multi-source-refresh-as-one-batch) chose one batch on purpose (fewer observer notifications, no mixed-age totals), and the product owner wants balances "as soon as possible". Options: keep one batch and define "as soon as possible" as fetched concurrently; write per network as each finishes (each write atomic and lane-ordered); or write coin and tokens first and staking and earn when they arrive.
- **D75** **S** **When the app asks for push permission.** Android composes the trigger from three flows (`AppViewModel.kt:88-94`: notifications available, Core's `isAsk`, a session, push off) and records the ask through `DevicePushSettings.stopAskNotifications`; iOS asks only when a create or import sheet is dismissed (`RootSceneViewModel.swift:159-167,230-240`) and never records the ask, so Core's 30-day re-ask ([`preferences/rules.rs`](../core/gemstone/src/services/preferences/rules.rs)) and the `has_asked` input of `notification_prompt` never see an iOS ask. ARCHITECTURE lists Android's prompt tracking as a one-sided feature. Decide whether both apps prompt on the same rule; then `should_ask_notifications` answers the whole condition (push state and wallet presence included) and both apps record the ask through Core. D48 settled the support prompt, a different trigger.

## What the sweeps taught

Read this before adding an item. Each rule below was learned by listing something that turned out not to be work, and each is stated once.

- **A sweep hit is a lead, not a verdict.** Confirm it by reading both apps before it goes on the list. Comparing the two apps first cut § 16 from 27 to 1 and § 29 from 5 to 0, and on 2026-09-23 cut eight scripted sweeps from about 500 raw hits to 16 items.
- **Count decisions, not names, files or members.** A test file named differently still covers the screen; a `var` that is a computed property is not state; a member count says nothing about ownership; a method named the same on both apps may compute different things (D15–D17). Pair a helper by what it computes.
- **The app maps; Core decides.** A `switch` over a Core enum that picks an icon, a colour, a keyboard or a localized label is the mapper contract working, not a decision. A label that *interpolates* a Core value into an app-localized sentence is where the localization belongs. A value type that only projects Core records needs no service. Moving a fixed string into Core adds an enum and a mapper per app without moving a decision (VM82–VM84).
- **A dash in the screen-service map means "not recorded", never "the other app decides this itself".** A coordinator or application case holding the service is the Android shape of holding it (§ 29).
- **Count a holder by the services it calls.** A reference passed straight through to the child that decides with it is a constructor argument (§ 23).
- **Every Core session is driven from both apps (N11, checked 2026-09-22).** Comparing each exported `on_*` and `view_state` call site per platform, the only differences left are equivalent routes, not hand-rolled transitions: Android reaches `GemAddAssetSession::on_chain` by passing the chain to `new_session` instead, and reads `is_transfer_loading()` as a cheap dedupe key where iOS reads the same field off the view state. A file-count comparison is not this check — it called four sessions one-sided that both apps drive.
- **A build setting is not a boundary, and a boundary is not a build setting.** `GemTests` "cannot link", the widget "cannot call Core" and `Formatters` "cannot import Gemstone" were each one missing build setting, and each had other items closed on its authority (§ 36). The reverse also happened: the widget target still carries a `libgemstone.a` linker flag from a four-day window in which it did call Core, and a survey read that as permission. The rule lives in the platform guide and the target's package dependencies say what it links; check those, not `OTHER_LDFLAGS`.
- **A method scan that matches `.name` misses calls made from an extension on the generated type** (VM8–VM13); grep the camel-case name with extensions and test directories included before calling an export dead.
- **Preview sample data and a shared helper inside `remember` are not feature-view Core calls** (VM72, VM75); a view that dispatches an opaque row key is the contract, not a leak.
- **A number crosses as a value and a style; a locale prints it.** Currency symbols, duration text, day grouping, dust and abbreviation thresholds rendered with the device locale are platform work once Core has decided the precision, the style and the tone (§ 17, § 19, § 21).
- **Ordering that must live in a database query stays there.** Core cannot write either app's query, and sorting a thousand rows in memory per emission is the wrong trade (§ 20). What Core can hand down is the order, limit and match the query applies (VM127).
- **A default arm can be the answer.** `None`, `false`, `Err` and a named `Unknown` in a provider table are fail-closed; only an arm that picks a wrong concrete value is a gap (§ 33). A blank string passed through as an error is not a default arm (AUD60).
- **Test the premise, not the count.** Composition depth was said to be where cycles appear: the graph was walked, 68 services, zero cycles (§ 31). File length was said to mean an outgrown module: the production halves are a smooth distribution and the rest is `mod tests` (§ 34). Two traits with different membership were one trait and its supertrait (§ 33). A survey called VM2 a parity bug and it was a duplicated rule with the same visible result.
- **A migration is the one place a rule does not get consolidated.** Its behaviour has already run on installed databases (§ 24).
- **Platform APIs for one intent are not two decisions.** Room's `EXTRA_IS_SENSITIVE` against `UIPasteboard`'s expiry date, a clock-driven lock screen, an OkHttp connection pool with no `URLSession` counterpart (§ 19, § 32).
- **Exclude on every sweep:** `Gem*Store` foreign-trait implementations, Hilt `@Provides`, Room `TypeConverters`, `@Preview` composables, framework overrides, `#Preview` bodies, generated files and test kits. All are called by generated or native code no token search can see.

### Decided and closed as correct

**AUD63 (2026-09-23).** Closed as correct: Reown walletkit 1.6.13's `Wallet.Model.SessionRequest` carries only `topic`, `chainId`, `peerMetaData` and the JSON-RPC `id`, `method` and `params`, with no expiry, so Android keeps passing `expiry = null` and relies on the SDK's `RequestExpired` event. Revisit when the Kotlin model exposes the expiry iOS reads.

**X172 (2026-09-22).** Closed, decided: stop handing the keystore to the apps. The three raw exports stay — `GemKeystoreConcurrencyTest` races several `GemKeystore` instances over one directory, both benchmarks time scrypt alone, and `MigrateV3KeystoreServiceTest` has no wallet store, so routing any of them through `GemWalletService` would test something else. What changed is who can call them. `GemKeystore` unlocks a wallet's secrets given a password, so an app holding one can sign without the service that decides whether signing is allowed, and both composition roots were handing it out: iOS read `storages.keystore.gemKeystore` at four sites in `ServicesFactory`, Android injected the Hilt binding from `GatewayModule` and `SwapModule`. Now each platform's keystore layer builds the four services that need it — `GemWalletService`, `GemSwapService`, `GemSignMessageService`, `GemAuthService` — and hands out those: `LocalKeystore+Services.swift` on iOS, where `gemKeystore` is `package` so `ios/Gem` cannot name it, and `KeystoreModule` on Android, the only module that injects the binding. No main source outside those two layers names `GemKeystore`, and a third `just check-boundaries` rule holds it there.

**D73 (2026-09-22).** Closed, decided: keep it silent. A WalletConnect simulation fails open and stays that way — a provider that cannot answer reaches the review as an empty result, which looks the same as a request that changes nothing. Carrying a "simulation unavailable" warning through the existing rows was the alternative and was not taken, so an outage never blocks signing and never adds a row. The policy is written down now rather than implied by an `unwrap_or_default`: [ARCHITECTURE § "A staged load names what each stage waits for"](ARCHITECTURE.md#a-staged-load-names-what-each-stage-waits-for) records it beside the scanner's fail-open, and `simulate_send_transaction` says it on the function.

**U17 (2026-09-22).** Closed, decided: match the app's rule in the widget. `WidgetValueTone` gives `GemPriceWidget` the same three-way answer Core's `valueTone` gives the app — a change of nothing is neutral, not a gain — so a flat 0% no longer reads green in the widget and grey in the app, and the colours come from the same `Colors` the app maps. It is a second copy of a Core rule, taken knowingly: the widget extension cannot link Gemstone without pulling the binary into a process with its own memory budget, which is the linkage problem this item always named. The copy is marked where it lives, so whoever moves the widget onto Core deletes it.

**D48 (2026-09-22).** Closed, decided: support asks, on both apps. `GemNotificationsService::enable_for_support` is the rule — it asks only when the os permission is available and push is not already on, so opening support twice never prompts twice — and both apps call it when the row is tapped. Android's composable no longer decides: it read `notificationsAvailable && !pushEnabled` itself and called `enableNotifications()`, which is the condition Core now owns, reached through a `EnablePushForSupport` case on `DevicePushSettings`. iOS gained the prompt it never had, through `SettingsViewModel.openSupport()`. The permission port is the existing `GemNotificationPermissions`; nothing new crosses.

**D72 (2026-09-22).** Closed, decided: always relock. `should_relock` no longer takes `has_pending_request`, so an open WalletConnect request cannot hold the lock off however long the app was away — which is what it did on Android, where `LockTimer` fed the flag, while iOS always passed `false`. `LockTimer` loses its `ActiveWalletConnectRequest` dependency and its two tests for the hold-off become one that asserts the opposite, and Core's rule test gains the case that an unbounded absence relocks.

**N4 (2026-09-21).** Closed as correct against [§ 7](ARCHITECTURE.md#a-service-never-hands-out-another-service). The eight iOS view models hold a second service only to pass it to the child that calls it: name resolution goes to `AddressInputViewModel` or `NameRecordViewModel`, the stake amount provider takes `GemStakeService`, and select-asset and perpetuals vend `RecentAssetsModel`. The parents themselves call only their screen service. The name service stays the shared-component dependency the parent passes down.

**U35 (2026-09-19, earlier subset).** Narrowed: `GemTransferData::transaction_type` and `GemPaymentService::decode_url` stay as [the compatibility notes](ARCHITECTURE.md#intentional-platform-differences-and-compatibility) record, and `GemPaymentService::transfer_destination` is read by the iOS `PaymentDestinationBuilder`. That earlier cleanup moved its other exports to plain `impl` blocks or deleted them, together with composition-service methods only Core calls and the replaced `HyperliquidSubscriptions` object. The remaining node helpers and fields landed with that export cleanup; this entry records the earlier narrowing only.

**K8 (2026-09-19).** Closed as correct against § 7. `GemStreamService` is the stream event router: each of its dependencies handles one event kind, so a single use each is its shape, and a composition service in front of it would add a hop per event. `GemAssetDetailsService`, `GemWalletService` and `GemPerpetualService` are screen services composing collaborators, which § 7 prescribes. Their only pure one-call forwards are `GemWalletService::address_url` to the explorer and `GemPerpetualService::add_recent` to recent activity, and § 7 names exactly that as the route by which a screen reads a composition answer.
