# Cross-Platform Awareness

Applies to every task. Both apps depend on the same Rust core and must stay aligned on shared product behavior; these rules say when a change in one place obliges a change elsewhere.

## Rules

1. Regenerate and verify the apps only when a `core/` change affects UniFFI interfaces, generated models, platform build inputs, or app-side integration:
   ```bash
   just generate
   just ios build
   just android build
   ```
   Internal Core implementation changes that preserve these contracts require relevant Core builds and tests, not iOS or Android builds. A passing Rust build is insufficient only when the change can affect app compilation or integration. Adding a variant to a generated enum the apps switch over (for example `SwapProvider` or `ChainType`) is an interface change: regenerate, then handle the new case in every exhaustive Swift and Kotlin switch on both platforms. If a regeneration's effect on either app is unclear, stop and restate before adding more changes.
2. Never write a catch-all branch over a Core enum. A Swift `default:` or a Kotlin `else ->` on a type Core owns turns the next variant Core adds into silent wrong behaviour on that platform only; listing every variant makes the compiler name each app that still has to decide. Group the variants that share an outcome into one arm rather than reaching for the catch-all. This applies to a boolean or optional query over the enum just as much as to a label map.
3. Implement parity or surface the gap. If a user-facing change should exist on both platforms, either implement both sides in the same task, or state the parity gap explicitly so it is not silently dropped. Before changing a screen's behaviour on one platform, read the sibling screen on the other and match its logic; the app that already solves the problem is the reference, and a simpler sibling is proof the machinery you were about to add is unnecessary. Two different mechanisms that happen to agree today are a parity gap, not parity.
4. Never edit generated files directly. Files headed `// Generated by` come from `core/` — change the source, regenerate, and commit the regenerated output when that generated area is tracked. Generated file locations:
   - **iOS**: `Packages/Primitives/Sources/Generated/` (generated models), `Packages/Gemstone/Sources/Gemstone/Gemstone.swift` and `Packages/Gemstone/Sources/GemstoneFFI/include/GemstoneFFI.h` (local ignored UniFFI bindings)
   - **Android**: `gemcore/src/main/kotlin/com/wallet/core/primitives/generated/` (generated models), `core/gemstone/android/gemstone/src/main/java/uniffi/` (local ignored UniFFI bindings, generated by the `:gemstone` Gradle module at build time)
   - **Pattern**: any file with a `// Generated by` header or under `uniffi/gemstone/`
5. Run `just localize` when changing shared localization inputs. Hardcoded user-visible strings on either platform are a bug.
6. Read chain capabilities from core's `ChainConfig` (`core/crates/primitives/src/chain_config.rs`). Hand-written per-chain capability lists in app code are forbidden — they drift from core.
7. Name and group feature modules the same way on both apps. A feature module is one product area with one page, `docs/product/<name>.md`, carrying the same name: PascalCase for the iOS package (`Features/<Name>`), snake_case for the Android module (`features/<name>`) and the page ([`docs/product/`](../docs/product)), whose `presents` and `viewmodels` packages are `com.gemwallet.android.features.<name>.presents` and `.viewmodels`. When a Swift name would clash with a type or an SDK module, both apps use the iOS name (`WalletTab`, `WalletConnector`). A new screen goes in the area module that holds it on the other app; add a module only for a new area, on both apps and with its page. A component several areas use lives in the shared UI package (`PrimitivesComponents`, `ui`), not in `Features/`; the QR scanner is the one shared feature module. Types inside a feature follow [ARCHITECTURE § Names](../docs/ARCHITECTURE.md#names).
